# V2-REV-010: Derive project universes from compiler-loaded inputs

Status: accepted

Date: 2026-08-14

Affected requirements: V2-ANA-001, V2-ANA-004, V2-ANA-007, V2-TS-001, V2-TS-002, V2-REP-004, V2-QLF-002, V2-QLF-003

Review perspectives: TypeSpec product, analysis/native, consumer/DX, qualification

## Existing decision

An analysis generation belongs to one exact project universe. Configuration chains, project roots,
project references, compiler and adapter versions, protocol, capabilities, and platform are part of
that universe. Incremental facts may advance only inside the same universe, while a changed universe
starts a complete lineage and a reader remains pinned to its prior generation.

The first native adapter violated that decision by accepting a caller-supplied universe identifier.
Changing a loaded `tsconfig`, project-reference root set, plugin version, or platform could therefore
produce a transaction under an identity that did not describe the resident compiler project.

## Proposed decision

- `NativeProjectDescriptor` contains only the requested root, configuration, capabilities, and
  module boundaries. It has no universe field and no caller override.
- The native driver derives the universe after loading the compiler project from the complete
  configuration chain, parsed root membership and project references, canonical module boundaries,
  requested capabilities, producer and protocol versions, exact `ttsc` and TypeScript-Go versions,
  and GOOS/GOARCH.
- Every identity input is portable. An external compiler input without a repository, package, or
  platform coordinate fails instead of embedding an absolute checkout path.
- A changed derived universe yields a complete base-less sequence-one transaction. The TypeScript
  service commits that transaction into the destination universe, reuses an existing identical
  generation when available, and never applies it as an increment to the prior universe.
- Restoring the exact prior compiler inputs may reuse their previously retained portable universe
  and generation.

## Evidence and motivation

The defect was reproduced by changing a configuration file and root set while retaining the same
caller seed: the original adapter kept the old universe. The production native now changes universe
for configuration and root-membership changes, emits a complete rollover, and restores the original
identity when the inputs are restored. Qualification also proves that caller seeding is absent,
incremental reuse survives ordinary source edits, and normalized incremental output equals a cold
build.

The public `ttsc` driver seams used for parsed configuration and root capture are the same class of
seam used by `ttscgraph`; TypeSpec owns only portable identity derivation and transaction adaptation.
The exact qualified production tuple is `ttsc` 0.25.0, its matching graph/toolchain artifacts,
TypeScript 7.0.2 / TypeScript-Go revision `56ab4af42157`, and protocol version 1.

## Alternatives

- Keep a caller seed and append compiler inputs later. Rejected because the seed remains a second
  authority and permits accidentally distinct identities for the same compiler project.
- Hash source contents into the universe. Rejected because source revisions belong to generations;
  doing so would destroy incremental lineage on every edit.
- Treat configuration changes as an ordinary generation increment. Rejected because compiler
  membership and option semantics define which facts can exist, not merely which facts changed.
- Use physical checkout or database identity. Rejected because worktrees and materializers must not
  rename the same logical project.

## Compatibility, migration, and gate effects

Callers delete the obsolete universe argument and observe `service.universe` as undefined until the
first successful refresh. Existing stores remain valid: a refresh either selects an already retained
derived universe or commits a new complete lineage. No persisted fact schema changes.

Gates 1, 2, and 4 are requalified with the exact production native binary. Gate evidence must include
root/configuration rollover, restoration reuse, caller-seed absence, and cold/incremental equivalence.

## Objections and dispositions

- Product objection: an initially undefined universe complicates status output. Resolved by making
  the first refresh the explicit compiler-authority boundary; presentation may report “unresolved”
  but may not invent an identity.
- Analysis objection: configuration hashing can become path-sensitive. Resolved by canonical
  repository, package, and platform coordinates plus fail-closed handling of unportable inputs.
- Consumer/DX objection: configuration edits now start a new lineage. Accepted because pretending
  continuity would make generation comparisons unsound; retained generations still make restoration
  fast.
- Qualification objection: restoration could accidentally reuse stale facts. Resolved by exact
  universe identity, content-addressed manifests, complete rollover validation, and differential
  cold proof.

## Consensus and decision

Accepted as a correction required by the already-ratified universe contract. No perspective retains
an unresolved soundness or migration objection. The native compiler is the only authority capable of
describing the project it actually loaded; TypeSpec validates and materializes that identity.
