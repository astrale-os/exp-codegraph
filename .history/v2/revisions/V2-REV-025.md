# V2-REV-025: Admit the measured richest-project transaction with bounded headroom

Status: accepted

Date: 2026-08-15

Affected requirements: V2-QLF-006, V2-QLF-007, V2-QLF-009, V2-QLF-010

Review perspectives: native protocol safety, self-host qualification, demand-driven analysis,
operational limits

## Existing decision

The process protocol independently bounds JSONL frames, assembled physical transaction bytes, and
decoded semantic Fact-payload bytes. Its provisional production defaults capped both transaction
budgets at 256 MiB. EXP-002 required both self-host corpora either to fit that provisional limit or
to ratify a measured replacement.

## Decision

- Keep individual frames at 64 MiB and streamed chunks at 8 MiB.
- Set decoded semantic payload defaults to 384 MiB and assembled physical transaction defaults to
  512 MiB.
- Preserve independent validation of both budgets before publication.
- Treat this ceiling as admission for an explicitly requested richest-capability transaction, not
  as a target unit of work. Ordinary consumers continue to request only the capabilities and
  payloads they need.

## Evidence and motivation

The frozen Kernel holdout's `backend/falkordb/tsconfig.json` project produced 268,454,479 semantic
Fact-payload bytes and a 365,326,188-byte assembled physical transaction. The Kernel Host project
later produced a 519,627,239-byte assembled physical transaction while remaining within the
independent 384 MiB semantic budget. The semantic producer
was rejected only 19,023 bytes beyond the provisional 256 MiB ceiling; after raising the TypeScript
default, a second fail-closed run exposed that the resolved physical default was not forwarded to
the native child. Resolved limits are now always explicit child-process arguments, and standalone
native defaults match the public adapter. Separate 384 MiB semantic and 512 MiB physical ceilings
admit the measured dimensions while retaining all frame, physical, semantic, digest, and
transaction admission checks.

The architectural response to large ordinary workloads remains demand-driven semantic depth,
affected-shard deltas, and selective hydration. Raising a bounded maximal-request ceiling does not
make full semantic export an interactive path and does not weaken exactness or memory safety.

## Alternatives

- Add a Kernel/project exception in qualification. Rejected: the reusable package must admit its
  supported maximal request through its ordinary public protocol.
- Remove or bypass the semantic budget. Rejected: decoded semantic size is the relevant memory-
  safety boundary and remains independently enforced.
- Redesign the representation before self-hosting. Rejected for this gate: representation spikes
  already showed useful body-byte reduction but did not justify a public semantic schema change;
  capability selection is the correct ordinary-path optimization.
- Use 512 MiB for both dimensions. Rejected: decoded semantic payloads fit the smaller 384 MiB
  safety boundary; only the encoded physical transaction needs 512 MiB.

## Compatibility and gate effects

The change affects only default admission limits. Callers may continue to provide smaller explicit
budgets. Protocol framing, fact schemas, identities, stores, and query behavior are unchanged.

## Objections and dispositions

- Objection: increasing the limit hides body inflation. Disposition: maximal export and ordinary
  demand-driven operations are separate products. The limit remains visible and finite; large body
  facts remain explicit self-host audit candidates rather than disappearing from evidence.
- Objection: physical bytes may differ from semantic bytes. Disposition: they have independent
  measured ceilings and are checked separately; neither can bypass the other.

## Consensus and decision

Accepted as the smallest measured production limit that self-hosts the frozen supported corpus
without corpus exceptions, while preserving the stricter demand-driven architecture for normal
consumers.
