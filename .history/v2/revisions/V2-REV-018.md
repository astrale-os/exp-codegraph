# V2-REV-018: Make exact query totals an explicit cost

Status: accepted

Date: 2026-08-15

Affected requirements: V2-ARC-005, V2-ANA-005, V2-ANA-013, V2-STO-001, V2-STO-007, V2-QLF-006

Review perspectives: Codegraph product, analysis/policy, persistence/query, consumer/DX, qualification/performance

## Existing decision

Generation-pinned fact and header pages expose an optional `total`, but every memory and SQLite page
currently computes the exact filtered cardinality whether or not the caller reads it. On SQLite this
adds a complete filtered `COUNT(*)` to point-like and cursor-page operations. Streaming exports
repeat that count for every internal page even though they only need the next cursor.

## Proposed decision

- `PageRequest.includeTotal` explicitly requests the exact filtered cardinality. It defaults to
  false.
- Without `includeTotal`, a page omits `total` and implementations must not perform a count-only
  scan. They fetch at most `limit + 1` matching envelopes to determine `nextCursor`.
- With `includeTotal`, `total` is exact for the generation and filter, independent of the cursor.
- Streaming exports never request totals. Policies that require a denominator request it explicitly
  once or consume a separately materialized aggregate when one is available.
- Memory, SQLite, and staged pass queries preserve identical behavior. This changes no fact,
  generation, cursor, manifest, or persisted-schema identity.

## Evidence and motivation

On the Codegraph all-capability diagnostic, payload-free body-header pages still took 8.6 to 10.2
seconds while an exact-ID header lookup took 4.4 milliseconds and selective hydration took 18.4
milliseconds. The page query was executing the same complete filtered count on every page. A full
header export therefore paid for dozens of redundant whole-result counts even though its required
complexity is one ordered scan.

The existing optional response field concealed a mandatory implementation cost. Making the request
explicit aligns the public API with the real complexity boundary and is smaller than introducing
cached counts, materialized aggregates, or a new storage schema before a consumer needs them.

## Alternatives

- Keep exact totals on every page and optimize the SQL. Rejected because exact cardinality remains
  linear in the filtered set and streaming would still repeat unnecessary work.
- Remove totals entirely. Rejected because bounded UI and policy consumers can legitimately need
  an exact denominator.
- Return an estimated total by default. Rejected because it weakens semantics and complicates
  cross-store equivalence.
- Add a materialized count table now. Rejected as premature: counts vary by every indexed filter
  combination, while most current consumers need only rows and a next cursor.

## Compatibility, migration, and gate effects

Callers that relied on an exact total add `{ includeTotal: true }`. Callers that already handled the
optional response field continue unchanged and become cheaper. No persisted data migration or
native protocol change is required.

Gate 6 adds cross-store tests for omitted and requested totals and performance evidence comparing
header point, page, full scan, selective hydration, and full semantic export. The optimization must
not be reported as reducing the unavoidable linear cost of a full semantic export.

## Objections and dispositions

- Product objection: an option makes pagination less automatic. Accepted because the response
  already declared `total` optional; the request now states when the expensive guarantee is needed.
- Policy objection: rules may silently use page length as the denominator. Resolved by requiring
  policies that need global coverage to request the exact total or consume a declared aggregate.
- Persistence objection: memory can count cheaply after filtering. Resolved by keeping identical
  semantics across stores; the contract must not disguise SQLite's algorithmic cost.
- Qualification objection: a faster page could merely omit correctness evidence. Resolved by exact
  total tests under `includeTotal`, cursor-equivalence tests without it, and unchanged cold semantic
  digests.

## Consensus and decision

Accepted as a bounded query-contract correction. It removes an observed repository-sized operation
from ordinary pages without changing semantic facts or committing Codegraph to a new index design.
