# V2-REV-005: Make public facts stable across source layout and compiler traversal

Status: accepted

Date: 2026-08-14

Affected requirements: V2-ANA-004, V2-TS-014, V2-TS-016, V2-TS-017, V2-TS-018, V2-TS-019, V2-TS-020, V2-CON-001, V2-QLF-011

Review perspectives: TypeSpec product, analysis/native, consumer/DX, qualification

## Existing decision

V2-REV-004 made complete exported declaration reachability authoritative, but limited the parity
exception to declarations with no surface observation issue. Public workspace identities still
copied V1's declaration byte offsets. Package ownership stopped at the first syntactically valid
`package.json`, even when it was nameless nested module-format metadata. Export origin and duplicate
error-code provenance were present in the contract but not yet deterministic in the native facts.

The first complete 303-module TypeScript-Go observation demonstrated that these are related
portability defects rather than useful V1 compatibility behavior. A resolved declaration can have
an explicitly partial normalized type while its symbol and owner remain certain. Unrelated text
insertions changed public IDs. Nameless `zod` and `hono` subpath manifests exposed pnpm-store paths,
and compiler source traversal selected different representatives for duplicate error codes.

## Proposed decision

- Public declaration identity is portable source coordinate plus qualified authored symbol path.
  Byte positions and compiler allocation order remain provenance only.
- Public closure follows every Checker-resolved declaration reachable from exports. A partial
  normalized type is retained as explicit completeness evidence but does not erase an independently
  resolved declaration or package owner.
- Package ownership walks past nameless nested manifests to the nearest named package. A malformed
  manifest still fails closed.
- Export facts follow local barrels and retain the authored external package source while semantic
  declaration identity continues to resolve through the Checker.
- Duplicate error-code provenance is selected after sorting portable source names, independent of
  TypeScript-Go's source visitation order.
- Gate 4 canonicalizes only the exact V1 defect class: positional declaration identities and an
  unowned physical dependency whose already-portable target file proves the named package. All
  other identity, ownership, reachability, and provenance differences still fail.

## Evidence and motivation

The full native corpus produced otherwise identical Core declarations with different byte offsets
than Node TypeScript, proving compiler position is not a cross-engine identity. It also found
package-owned `zod/v4/core` and `hono/dist/types` files classified as `unowned:node_modules/.pnpm/*`
because their nearest subpath manifests deliberately omit `name`. Several public APIs reached
resolved Core Domain declarations whose type normalization reported unsupported generic shapes;
rejecting those edges discarded known ownership because a different fact was partial.

The production-native adversarial fixture now moves a public declaration by inserting unrelated
source text and requires identical public IDs. It includes a nameless nested package manifest,
direct external re-export provenance, and existing cold/incremental equivalence. The full-corpus
parity runner enumerates every accepted closure and ownership correction.

## Alternatives

- Keep byte offsets and add a secondary stable key. Rejected because downstream graph joins would
  still encounter the unstable public identity as the canonical key.
- Hash full declaration text. Rejected because harmless formatting and body edits would rename a
  semantic declaration, and the Checker already supplies canonical symbol ownership.
- Drop declarations with partial type representations from dependency closure. Rejected because it
  conflates type-shape completeness with symbol-resolution completeness and makes impact analysis
  knowingly incomplete.
- Treat every nested manifest as a package boundary. Rejected because common package subpaths use
  nameless manifests only to select module semantics.
- Copy V1's first observed code location. Rejected because compiler traversal is not a portable
  ordering contract.

## Compatibility, migration, and gate effects

Persisted V2 shadow facts produced before this revision are regenerable and receive new declaration
IDs; none are authoritative before Gate 5. Consumers gain IDs stable under unrelated insertions,
correct package nodes, external re-export provenance, and deterministic diagnostic navigation.
Source spans remain available for editors and are refreshed normally.

Gate 4 remains fail-closed. The compatibility projection removes only numeric position/kind suffixes
from V1 declaration coordinates and rewrites only physical unowned package targets already proven by
a `package:` target-file coordinate. Closure additions must still be API-only, type-only,
`<public-type-closure>` occurrences whose declarations exist and are reachable in the source module
fact. No implementation import or unresolved edge can pass through these predicates.

## Objections and dispositions

- Product objection: IDs change from V1. Accepted because V1 IDs change after unrelated edits and
  are unsuitable for an incremental index; V2 has not crossed authority yet.
- Analysis/native objection: same-spelled declarations could collide. Resolved by retaining portable
  source coordinates and qualified lexical ownership; synthetic declaration-less exports remain
  separately guarded.
- Consumer/DX objection: a partial declaration may now add many dependency edges. Accepted as
  truthful graph data; presentation may aggregate by package/module without deleting exact facts.
- Qualification objection: canonicalization could hide arbitrary identity drift. Resolved by the
  narrow positional parser, collision checks, stable-ID edit fixture, exact source/target tuple
  comparison, and enumeration of every accepted relationship.

## Consensus and decision

Accepted as a pre-authority V2 correction under the owner's direction to build a reusable,
incremental, headless foundation above ttsc rather than reproduce V1 defects. The change strengthens
semantic stability and provenance without adding a second resolver or Checker, and preserves the
deep capability hierarchy with flat cohesive implementation files inside the native leaf module.
