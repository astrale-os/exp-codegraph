# V2-REV-017: Add payload-free fact discovery before selective hydration

Status: accepted

Date: 2026-08-15

Affected requirements: V2-ARC-005, V2-ANA-005, V2-ANA-009, V2-ANA-013, V2-STO-001, V2-STO-007, V2-QLF-006

Review perspectives: Codegraph product, analysis/policy, persistence/query, consumer/DX, qualification/performance

## Existing decision

Generation-pinned queries support indexed filtering and pagination, but every selected row is
returned as a complete `Fact`, forcing payload reconstruction even when a consumer only needs IDs,
namespaces, kinds, subjects, completeness, provenance, or evidence. Under compressed shard
materialization, reconstructing one fact can also decompress its physical payload block. Policies
and discovery passes therefore cannot perform a cheap metadata selection before deciding which
payloads actually need semantic admission.

## Proposed decision

- Generic queries expose immutable `FactHeader` pages, exact-ID lookup, and streaming export in
  addition to existing hydrated fact operations. A header is exactly the fact envelope without
  `payload`; it retains generation, schema, completeness, provenance, evidence, and derivation
  inputs.
- Header filters and ordering have the same generation-pinned semantics as hydrated fact filters.
  Header cursors remain opaque and bound to the exact generation and filter.
- A header operation may read normalized envelope, evidence, and input indexes, but it must not
  decode a semantic payload, decompress a physical payload block, or populate a payload cache.
- Consumers select headers first and hydrate only exact required fact IDs. Full semantic export
  remains explicit and linear in all selected semantic bytes.
- Memory, SQLite, and staged portable-pass queries implement the same contract. The generic API
  remains language-neutral; typed semantic readers continue to admit payloads only after hydration.

## Evidence and motivation

The Codegraph all-capability diagnostic contains 73,449 facts and 225.6 MB of semantic fact bytes.
Many candidate and policy decisions begin with fields already normalized in the fact envelope.
Reconstructing large body payloads merely to reject them by namespace, kind, subject, completeness,
or provenance is avoidable work and obscures the physical/semantic representation boundary.

SQLite already indexes those filter dimensions separately from payload materialization. Exposing the
existing physical separation through a stable headless query contract is smaller and safer than
adding language-specific SQL or returning database row IDs.

## Alternatives

- Keep `facts()` and ask consumers to ignore `payload`. Rejected because payload reconstruction has
  already happened before the consumer can ignore it.
- Return SQLite row IDs or physical shard ordinals. Rejected because they are local storage details,
  unstable across materializers, and not portable semantic identities.
- Add TypeScript-only candidate SQL. Rejected because the query/store foundation must remain
  language-neutral and policies should compose portable facts rather than database schemas.
- Automatically make every `facts()` call lazy. Rejected because a semantic `Fact` promises a
  readable admitted payload; hidden asynchronous payload access would complicate failure and
  lifetime semantics.

## Compatibility, migration, and gate effects

The API is additive. Existing `facts`, `factsById`, and `export` behavior is unchanged. No SQLite
schema or persisted identity changes; existing databases gain the query behavior immediately.

Gate 6 gains memory/SQLite equivalence, cursor, filtering, exact-ID, physical-codec, and corrupt or
unavailable payload tests proving header access remains payload-free. Performance qualification must
measure point, page, header scan, selective hydration, and full export separately; a faster header
scan cannot be reported as a faster full semantic export.

## Objections and dispositions

- Product objection: another query shape increases API surface. Accepted because it represents a
  real semantic/physical boundary and replaces ad hoc store-specific discovery rather than
  duplicating an existing cheap operation.
- Analysis/policy objection: provenance can itself be large. Accepted; provenance is required for
  attributable selection and remains normalized. A later minimal index view would need separate
  evidence and cannot weaken `FactHeader` identity.
- Persistence objection: header and fact query implementations could drift. Resolved by shared
  filters/cursors, one row-to-header admission function, and cross-store contract tests.
- Consumer/DX objection: callers may forget to hydrate required payloads. Resolved by the distinct
  `FactHeader` type, exact `headersById`/`factsById` names, and typed readers continuing to return
  only admitted full facts.
- Qualification objection: a mock returning headers without payload does not prove SQLite avoids
  decompression. Resolved by an instrumented physical codec and compressed-store tests where header
  operations leave decode counters unchanged and hydration increments them.

## Consensus and decision

Accepted under the user's direction to remove broad payload reconstruction from ordinary queries
and policies while avoiding a storage-engine redesign that measurements have not justified. The
product, analysis, persistence, consumer, and qualification perspectives agree that a payload-free
portable header is the narrow reusable seam; no unresolved objection violates soundness or the
Kernel consumer boundary.
