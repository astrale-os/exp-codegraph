# V2-REV-008: Own normalized materialization and reuse Codegraph selectively

Status: accepted

Date: 2026-08-14

Affected requirements: V2-STO-001, V2-STO-003, V2-STO-004, V2-STO-005, V2-STO-007, V2-QLF-004

Review perspectives: TypeSpec product, analysis/native, consumer/DX, qualification

## Existing decision

TypeSpec V2 owns immutable fact generations behind interchangeable memory and SQLite contracts.
The initial SQLite reference implementation serialized every retained generation into one
`snapshot_json` database value. The ADR rejected an external graph database service, but did not
name or meaningfully evaluate Codegraph, a local Apache-2.0 package with substantially more mature
normalized SQL, query, churn, AST, CFG, and dataflow machinery.

## Proposed decision

- TypeSpec and `ttsc` retain semantic authority: portable identities, versioned facts,
  provenance, completeness, pass DAGs, immutable generations, body semantics, bounded values, and
  policy conformance do not adopt Codegraph's ontology.
- TypeSpec has no direct runtime dependency on `@optave/codegraph` and does not maintain a
  wholesale fork.
- The production SQLite store is TypeSpec-owned, normalized, and content-addressed. Generations
  reference immutable shards; indexed fact envelopes, evidence, and inputs replace complete
  snapshot JSON values.
- The snapshot-JSON store remains correctness/migration evidence only.
- Generic Codegraph machinery or tests may be copied or adapted selectively after source review.
  Every derivative pins the upstream revision, preserves Apache-2.0 attribution, marks
  modifications, and records semantic divergences.
- Ownership is the default, not a temporary adapter strategy. Reuse is admitted only at the
  mechanism level: a bounded routine, schema/indexing pattern, or adversarial test whose purpose
  remains generic after all Codegraph identities, lifecycle assumptions, and product ontology are
  removed. A copied subsystem, compatibility layer, or continuing synchronization burden is a fork
  and requires a new architectural decision.
- Conceptual influence, adapted tests, and copied implementation text are distinguished in
  provenance. Independently implemented patterns carry no upstream code claim; adapted or copied
  text carries file-level attribution and is qualified against TypeSpec's own contracts.
- Codegraph's fixed graph schema, Tree-sitter analysis, row/line identities, mutable-current
  lifecycle, synchronous change journal, and mirrored native/WASM implementation are excluded.

## Evidence and motivation

The source-level spike against Codegraph 3.16.0 revision
`11475e7c0f36fd3fcb482dd3ea65f6d5845049b3` found no public compiler-fact ingestion, arbitrary
fact registration, generation-pinned reader, or query-extension protocol. A sidecar retained
namespaced generations across Codegraph rebuilds, but had to reimplement transactions, leases,
retention, validation, provenance, completeness, and queries.

Adversarial qualification found missed same-process configuration changes, missed
`tsconfig`-only alias changes, stale create/delete/rename metrics, and incremental/cold divergence
after position and branch-like body churn. Codegraph AST and CFG rows remain useful supplemental
evidence, but the fixture did not provide checker-exact SDK identity or bounded
`known | unknown | ambiguous | unsupported` results.

The same audit identified reusable operational lessons: compound SQLite indexes, WAL and bounded
writer behavior, parameter-bound filtering, bounded pagination, purge-oriented churn fixtures, and
normalized incremental-versus-cold comparisons. Those can improve V2 without importing a second
semantic authority.

The current normalized materializer uses those lessons but copies no Codegraph source file
verbatim. Future copying is an exceptional implementation choice, not the preferred integration
path: it must be smaller and cheaper to maintain than an independent implementation, survive
removal of Codegraph-specific assumptions, and demonstrate a concrete correctness, performance, or
maintenance benefit.

## Alternatives

- Depend directly on Codegraph through an adapter. Rejected because duplicate parsing remains
  mandatory while nearly all V2 semantic and generation infrastructure stays in the adapter.
- Contribute extension seams and wait. Rejected as the production dependency boundary; upstream
  contributions may still be useful, but the required seam spans schema, lifecycle, ingestion, and
  query ownership rather than one narrow hook.
- Maintain a narrow Codegraph fork. Rejected because the necessary delta is not narrow: it would
  replace analysis input, storage semantics, identity, lifecycle, and public queries.
- Reuse only Codegraph's schema unchanged. Rejected because its fixed nodes/edges and mutable IDs
  would overfit V2 facts to a different product ontology.
- Keep snapshot JSON as production persistence. Rejected because every carried shard is rewritten,
  indexed filtering requires deserializing complete generations, and database size scales with
  repeated snapshots rather than changed semantic content.

## Compatibility, migration, and gate effects

The public `AnalysisStore`, `AnalysisQuery`, fact, generation, and transaction contracts do not
change. Existing prerelease schema versions migrate through semantic snapshot validation into the
normalized schema. The database remains regenerable and can be removed after an incompatible or
corrupt migration.

Gate 4 now requires the named Codegraph decision evidence, normalized-schema proof, identical
memory/SQLite transaction suites, crash/corruption/migration coverage, and cold/incremental
equivalence after create, edit, delete, rename, configuration, and branch-like churn. No Codegraph
benchmark result can waive a semantic or lifecycle incompatibility.

## Objections and dispositions

- Product objection: owning SQLite may duplicate mature work. Resolved by explicitly allowing
  selective source-derived reuse and test provenance while refusing product-specific ontology.
- Analysis objection: dropping Codegraph loses ready-made AST/CFG/dataflow. Resolved because `ttsc`
  already owns exact AST/Checker extraction; supplemental Codegraph evidence can be revisited as an
  independent consumer, not authority.
- Consumer/DX objection: a custom store may expose SQLite details. Resolved by preserving the
  generic headless query contract and keeping schema/connection types private.
- Qualification objection: conceptual reuse can hide copied defects or license obligations.
  Resolved by revision pinning, attribution, modified-file notices, divergence documentation, and
  differential cold oracles. The provenance record must also say whether reuse is conceptual,
  test-adapted, or implementation-derived; absence of that classification rejects the derivative.
- Scalability objection: normalized rows can increase insert count. Accepted with content-addressed
  shard reuse, prepared writes, compound indexes, bounded pages, and real-corpus latency/size gates.

## Consensus and decision

Accepted before Gate 4 persistence qualification. The product direction explicitly prefers owning
the reusable headless machinery over a direct Codegraph dependency, provided reuse remains
selective and evidence-based. The revision keeps TypeSpec above `ttsc`, preserves the semantic
contracts already ratified, and replaces only the prototype persistence representation.
