# V2-REV-002: Give dependency relationships stable identity and complete occurrence evidence

Status: accepted

Date: 2026-08-13

Affected requirements: V2-ANA-004, V2-TS-004, V2-TS-014, V2-CON-001, V2-QLF-011

Review perspectives: TypeSpec product, analysis/native, consumer/DX, qualification

## Existing decision

V1 groups module dependencies by source module, target module, relationship kind, source file, and
target file. The retained object nevertheless keeps the identity, source location, import spelling,
and flags of whichever contributing declaration or syntax occurrence happened to be visited first.
Reordering exports or compiler traversal can therefore change a graph edge identity without
changing the dependency, and the other contributing occurrences disappear from the projection.

## Proposed decision

A V2 module dependency is one logical relationship identified from its source module, target
module, kind, source file, and target file. Its identity is a portable content-derived analysis ID
and does not contain a representative source location. Every contributing import, export, dynamic
load, side-effect import, or public-type-closure declaration is retained in a canonically ordered
`occurrences` collection with its own identity, flags, spelling, location, and optional declaration
identity.

Conformance evaluates relationship-level ownership once and occurrence-level properties such as a
deep import against every occurrence. It never selects a semantically privileged representative.

## Evidence and motivation

Full-corpus shadow comparison exposed equal logical dependency tuples whose V1 and V2 IDs named
different declarations solely because V1 retained the first traversal result. The existing
`TYPESCRIPT-OCCURRENCE-PRESERVATION` law already requires independently attributable evidence after
relationship deduplication. The production-native adversarial fixture now creates two syntax
occurrences for one relationship and proves one stable edge retains both distinct occurrences.
Conformance regression coverage proves policy still evaluates the richer portable fact.

## Alternatives

- Reproduce V1 traversal order. Rejected because compiler iteration is not a semantic contract and
  would encode the known instability into durable indexes.
- Pick the lexically first occurrence. Rejected because it makes output deterministic but still
  discards evidence and gives one occurrence accidental authority.
- Emit one edge per occurrence. Rejected because topology consumers need a compact relationship
  graph and would have to rediscover the same grouping inconsistently.
- Keep a representative beside the occurrence set. Rejected because no consumer need justifies a
  second, potentially contradictory source of truth; presentation can select an occurrence openly.

## Compatibility, migration, and gate effects

This changes the pre-authoritative V2 TypeScript fact API. Consumers migrate from singular
`specifier`, `typeOnly`, `deep`, and `location` fields to the ordered occurrence collection.
Relationship queries become stable across occurrence reordering. Gate 4 parity compares exact
logical edge coverage, proves the V1 representative remains included in V2 evidence, and reports
the richer identity/evidence representation under `V2-DRIFT-003`; all other differences still fail.
No V1 application is changed before the Gate 5 authority switch.

## Objections and dispositions

- Product objection: a diagnostic still needs one clickable location. Resolved by emitting one
  diagnostic per violating occurrence; presentation may group them without changing evidence.
- Analysis/native objection: larger facts may increase storage. Accepted as bounded by actual
  dependency occurrences, with the topology edge stored once and occurrence evidence deduplicated
  by identity.
- Consumer/DX objection: the richer shape is less convenient for simple topology. Resolved because
  relationship-level source, target, kind, and files remain directly available; only properties
  that can differ between occurrences move into `occurrences`.
- Qualification objection: richer V2 evidence cannot be byte-equal to a lossy oracle. Resolved by a
  named, fail-closed comparator that requires exact logical edge coverage and inclusion of every V1
  representative while reporting accepted drift separately from unexplained failures.

## Consensus and decision

Accepted under the TypeSpec owner's explicit direction that oracle flaws must be tracked and
justified rather than copied into V2. All four perspectives have a concrete disposition, the change
strengthens the ratified occurrence-preservation and identity laws, and no Kernel safety or
consumer requirement depends on traversal-selected representatives.
