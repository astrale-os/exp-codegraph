# V2-REV-020: Admit SQLite deltas without repeated fact-by-fact closure queries

Status: accepted

Date: 2026-08-15

Affected requirements: V2-QLF-006

Review perspectives: persistence, concurrency, semantic equivalence, performance, failure recovery

## Existing decision

SQLite validates a producer transaction before acquiring its cross-process writer lock and repeats
the complete validation after acquiring the lock. Fact-closure admission issues one indexed query
per changed fact and derivation input. This is sound, but a Kernel private edit with 14 changed
shards and 492 changed facts spends approximately two seconds in SQLite admission even though it
does not rewrite any unaffected shard payload.

## Proposed decision

- Complete semantic transaction, manifest, shard, and fact-closure validation runs once against the
  indexed current generation before the writer lock.
- Fact identity, external derivation input, removed-fact, and unaffected-consumer checks are
  set-oriented queries over the exact changed fact and shard sets. They never hydrate semantic
  payloads from unaffected shards.
- After `BEGIN IMMEDIATE`, admission rechecks the exact current generation identity and sequence.
  A concurrent writer advancing the lineage produces `BASE_STALE`; otherwise the already-admitted
  immutable transaction remains valid and is not semantically rescanned.
- Payload encoding remains outside the writer lock. The locked phase writes only changed
  content-addressed shard rows, the new immutable generation membership, and its current pointer.

## Evidence and motivation

The pre-change Kernel SQLite diagnostic measured 2,784.15 ms for the private edit. SQLite commit
consumed 1,996.50 ms, including 951.64 ms for the repeated locked validation, and the end-to-end
speedup over its independent cold oracle was 12.44 times.

With set-oriented closure admission and the causal base-only locked recheck, the same exact edit
measured 1,046.77 ms. SQLite commit consumed 89.57 ms and the locked recheck 0.051 ms. The producer
still projected one source and one module, sent 14 shard upserts and two deletes, and reconstructed
the exact independent cold generation. This is a diagnostic comparison; system load made the cold
samples non-comparable, so it is not frozen counterbalanced performance evidence.

## Alternatives

- Remove locked validation entirely. Rejected because a separate process can advance the current
  generation while this writer waits for `BEGIN IMMEDIATE`.
- Repeat complete validation inside the lock. Rejected because only the causal current lineage can
  change between the synchronous pre-lock admission and the acquired lock; immutable shard content
  and the caller's transaction cannot change during the blocking call.
- Trust producer-declared fact closure. Rejected because the store remains the admission boundary
  and must independently reject duplicate facts, missing inputs, and removed facts still consumed
  by unaffected shards.
- Persist a new delta-manifest schema now. Deferred because immutable generation membership is not
  the measured bottleneck: the existing write phase is approximately 27 ms for 2,305 references.

## Compatibility, migration, and gate effects

There is no public API, fact schema, database schema, transaction protocol, identity preimage, or
query behavior change. Existing memory/SQLite equivalence, stale-base, rollback, cross-process
serialization, crash recovery, migration, and corruption tests remain authoritative.

Gate 6 still requires repeated counterbalanced Codegraph and Kernel trials plus explicit database
row attribution before V2-QLF-006 can become qualified. This revision is implementation evidence,
not permission to hand-author governed performance evidence.

## Objections and dispositions

- Concurrency objection: pre-lock validation may observe a stale base. Resolved by comparing both
  semantic generation identity and sequence after the writer lock is acquired.
- Closure objection: batching could weaken error detection. Resolved by preserving all four checks:
  duplicate changed identities, unavailable external inputs, removed facts, and unaffected consumers
  of removed facts. Existing differential store tests pass unchanged.
- Portability objection: set queries rely on SQLite JSON table functions. Accepted because JSON
  functions are part of the SQLite runtime embedded by supported Node releases and already underpin
  the store's normalized JSON envelopes.

## Consensus and decision

Accepted as a persistence-local algorithmic correction. It removes repeated per-fact round trips
and redundant locked semantic validation while preserving SQLite as the independent transactional
admission boundary.
